# Chapter 3 — Domain Model

## 3.1 Introduction

The USO Enterprise Platform is designed according to Domain-Driven Design (DDD)
principles.

Instead of organizing the software around database tables or UI screens, the
system is organized around business domains. Each domain encapsulates its own
business rules, entities, services, workflows, and history.

The objective is to ensure that future modules (Budget, Battery, Power, Invoice,
AMP, AI, etc.) can be added without redesigning the existing architecture.

## 3.2 High-Level Domain Model

```
USO Enterprise Platform
│
├── Master Data Domain
├── Work Item Domain
├── Assignment Domain
├── Contractor Domain
├── Health Check Domain
├── Drive Test Domain
├── Acceptance Domain
├── Letter Domain
├── Dashboard Domain
├── Reporting Domain
├── Notification Domain
├── Action Center Domain
├── Administration Domain
└── Audit Domain
```

## 3.3 Master Data Domain

**Purpose:** Maintains all reference information imported from CPM.

**Owner:** Project Manager

**Main Entities:** Province, Village, Site, Technology, Site Type, Region,
Contractor, Problem Category.

Master Data cannot be manually created except by Admin. Most records originate
from CPM.

## 3.4 Work Item Domain

The Work Item is the core **Aggregate Root** of the entire platform. Everything
revolves around Work Items.

**Primary Key:** SiteID + SiteType

**Contains:**

- Requested Technology
- Assignment Information
- DT Status
- Acceptance Status
- Contractor
- Battery Status (Future)
- Budget Status (Future)

Every other operational entity references Work Item.

## 3.5 Village Domain

Village belongs to a Work Item.

```
One Work Item
   ↓
Many Villages
```

Each Village owns: ICT Status, CRA Status, Technology Approval, Letters,
History.

## 3.6 Assignment Domain

Responsible for contractor allocation.

```
Official Assignment
   ↓
Contractor Assignment
   ↓
Assignment History
   ↓
Reassignment
```

Assignment history is immutable.

## 3.7 Contractor Domain

Maintains contractor information. Includes: Company, Users, Assigned Work Items,
Performance, Monthly Progress, Blocked Sites, KPIs.

## 3.8 Health Check Domain

**Purpose:** Determine DT readiness.

**Possible Results:** Ready, Blocked.

Blocked requires: Problem Category, Comment, History.

**Owner:** Contractor

## 3.9 Drive Test Domain

```
One Work Item
   ↓
One Active Drive Test
   ↓
Many Historical Drive Tests
```

The latest approved DT is the active one. Rejected DTs remain in history.

Drive Test contains: Execution Date, Report Link, Status, Coordinator Review, PM
Review, Remarks.

## 3.10 Acceptance Domain

Acceptance belongs to Village.

```
Work Item
   ↓
Village
   ↓
Acceptance
```

Each Acceptance contains: ICT, CRA, Technology Status, Overall Status, History.

## 3.11 Technology Approval Domain

Every Village contains **2G, 3G, 4G**.

Each technology has: Approval Status, Approval Date, Comment, Commitment.

Technology approvals are independent.

## 3.12 Letter Domain

Letters are independent entities.

```
One Letter
   ↓
Many Villages
```

Stores: Letter Number, Authority, Province, Issue Date, PDF, Comment, History.

## 3.13 Dashboard Domain

Dashboard never stores data. Dashboard reads data. Everything is calculated
dynamically. No duplicated statistics.

## 3.14 Reporting Domain

Reports are generated dynamically.

**Supported Outputs:** Excel, PDF, CSV (Future), Power BI API (Future).

## 3.15 Notification Domain

Notifications are generated by Events.

Examples: Assignment Created, DT Completed, DT Rejected, ICT Approved, CRA
Approved, CPM Conflict, PM Decision Required, Coordinator Action Required.

Notifications are never manually created.

## 3.16 Action Center Domain

Action Center is not a table. It is a **Rule Engine**. Rules generate pending
tasks.

Example:

```
IF DT Approved AND PM Approval Missing
   ↓
Generate PM Task
```

Example:

```
ICT Reject
   ↓
Coordinator Task
   ↓
Notify Contractor
```

Future modules automatically plug into Action Center.

## 3.17 Administration Domain

Responsible for: Users, Roles, Permissions, Reference Data, System Settings,
Imports, Exports, Audit.

## 3.18 Audit Domain

Every operational change creates an **Audit Event**. Audit Events are
append-only and never editable.

Stores: Timestamp, User, Module, Old Value, New Value, Reason.

## 3.19 Aggregate Roots

To avoid circular dependencies, only the following entities act as Aggregate
Roots:

- Work Item
- Contractor
- User
- Letter
- Notification

Everything else belongs to one Aggregate.

## 3.20 Domain Events

The system is event-driven. Examples:

```
CPMImported
AssignmentCreated
AssignmentChanged
HealthCheckCompleted
DriveTestSubmitted
DriveTestRejected
DriveTestApproved
ICTSubmitted
ICTApproved
ICTRejected
CRASubmitted
CRAApproved
CRARejected
LetterRegistered
PMApproved
CPMConflictDetected
```

Each Event automatically updates:

- Dashboard
- Reports
- Notifications
- Action Center
- Audit Log

## 3.21 Domain Services

Some business logic belongs to services instead of entities. Examples:

- Assignment Service
- Drive Test Service
- Acceptance Service
- Dashboard Service
- Reporting Service
- Notification Service
- Workflow Service
- CPM Import Service
- Audit Service

Services encapsulate complex workflows and orchestration.

## 3.22 Domain Invariants

The system shall always enforce the following invariants:

1. A Work Item cannot exist without a Site.
2. A Village cannot exist without a Work Item.
3. A Contractor Assignment must reference exactly one active Contractor.
4. A Work Item may have only one active Contractor Assignment.
5. A Work Item may have only one active Drive Test.
6. Historical Drive Tests shall never be modified.
7. A Village may have multiple Letter references over time.
8. Acceptance status is always derived from ICT and CRA decisions.
9. Dashboard values are always calculated, never stored.
10. History records are immutable.
11. CPM remains the master source for infrastructure data.
12. No operational record shall be physically deleted.

## 3.23 Future Domains

The architecture reserves dedicated domains for future expansion:

- Budget Domain
- Battery Domain
- Power Domain
- Invoice Domain
- AMP Integration
- AI Recommendation Engine
- Predictive Analytics
- Document Management
- API Gateway

Each future domain will reference existing Aggregate Roots rather than
duplicating operational data.

## 3.24 Domain Dependency Diagram

```
Master Data
      │
      ▼
 Work Item
      │
 ┌────┼───────────┐
 ▼    ▼           ▼
Assignment   Health Check   Village
      │           │          │
      ▼           ▼          ▼
 Drive Test      Action Center
      │
      ▼
 Acceptance
      │
      ▼
 Letters
      │
      ▼
 Dashboard
      │
      ▼
 Reports
```

Dependencies flow in one direction only, preventing circular references and
simplifying maintenance.
